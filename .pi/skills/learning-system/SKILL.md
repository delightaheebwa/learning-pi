# Learning System

The active learning system, running in pi against the learning-system repository working copy (the current working directory).

**Trigger routing (read first):**
- **"review" → review flow** (active track). Runs in the main session.
- **"solo" / "AI-free check" / "closed-book" → solo flow** — a closed-book review of the active track where the gate withholds teaching (`SOLO_NO_TEACHING`). Same deterministic queue and close as the review flow, but `review-clerk` records every attempt with `mode:"solo"` so it feeds the independence gate. Teaching and hints are impossible by construction; grade the closed-book answers only.
- **"teach me X" / "learn" / "study" → teaching loop** — use the `learning-teach` skill, NOT a review. "review" alone means the review flow.
- **"lesson" / "continue" → next curriculum lesson** — use the `learning-teach` skill.

**Position discipline (read first):** the current lesson/phase is **not** recorded in this skill. Derive it at runtime from `Learning System/CURRICULUM.md`, `Learning System/MISSION.md`, and the newest files in `Learning System/Lessons/` + `Learning System/Sessions/`. If those disagree, **STOP and report the contradiction to the user** before doing any work; do not guess or merge. (This repo has known stale statuses; treat the state files as the only source of position.)

**Turn tags (required — enforced by the gate):** begin every assistant message with `[[TURN:claims]]` (teaching/claims/plan), `[[TURN:quiz]]` (question batch), `[[TURN:grade]]` (grading a learner answer), or `[[TURN:none]]` (transitions/summaries). The gate strips the tag before the learner sees it and withholds a message whose tag is missing or unsupported by a matching, passing verification receipt. A dropped tag is recovered from a bound receipt (`grade`/`quiz` from `grade-audit`/`quiz-audit`, `claims` from a `fact-check` whose `rendered_content` covers the text); `none` is not inferred for ordinary turns — the only implicit `none` is the ingest/review close summary after its writer/audit returns. Dispatch each verifier **once per turn** with `dispatch({ agent, task: { ...envelope... } })` (foreground) — never re-verify the same draft; on a match/binding withhold, re-emit the verified text or fix the tag.

## Context discipline (hard rules — read first)

Sessions die when the running conversation outgrows the model's context window: every tool output stays in the transcript forever. The fix is fewer, denser tool calls — not smaller messages.

- **Batch all reads.** Never chain multiple full-file reads for state. Use the batch tool ONCE (`python3 scripts/ops.py ...`, paths are repo-root-relative):
  - Session start: `python3 scripts/ops.py state <track>` (reviews: `state <track> --review` for the compact profile + due queue)
  - Any mix of ranges/tails/greps: `python3 scripts/ops.py bundle "PATH:N-M" "PATH:-N" "PATH@regex1|regex2"`
- **Read wiki pages by section.** First `bundle "Knowledge Wiki/wiki/<page>.md@^## "` to list headings, then fetch only the section you enrich.
- **Batch all writes.** Persistence at session end = ONE apply call, not N writes:
  `python3 scripts/ops.py apply <<'SPEC'` then a JSON spec, then `SPEC`.
  Spec: `{"writes":[{"path","content"}],"appends":[{"path","content"}],"replaces":[{"path","find","replace_with"}]}`.
- Target **≤12 tool calls per flow**. Never re-read a file already in context. Never dump whole files you only need one row of. For git, use `git diff --stat` (not a full diff) and `git diff -- <path>` only for a file you need; do not switch models mid-flow (it invalidates the prompt cache and re-bills the whole context).

## State files (relative to the working repository root)

- `Learning System/Core/💡 Learning Profile.md` — learner preferences. Read at session start.
- `Learning System/Core/📚 Active Concepts.md` — per-track concept rows with `Type` (`memory | concept | procedure | design`). Type drives scheduler intervals. Grep/range only the needed track — never the whole file; `📦 Concept Archive.md` is out of scope.
- `Learning System/Core/Attempts.json` — evidence-based mastery sidecar (attempt history, interval_index state machine, Feynman pass). Bundled by `ops.py state`; report via `ops.py mastery <track>` — **advisory only** (scores shown, not blocking). `ops.py mastery` reports per-dimension scores (recall, conceptual, procedural, transfer, independence, stability) plus per-concept `calibration` and `transfer_ok`; a dimension with no evidencing attempt shows `—` (unknown), never 0. `ops.py attempt` accepts optional `--confidence sure|hunch|no-idea`, `--hints N`, `--mode normal|solo` (solo = AI-free), and `--prereq NAME` (repeatable); `--qtype` is an enum (unknown values rejected). A failed `mode=solo` attempt blocks the `solid` tag via the independence gate; a `concept`/`design` entry cannot be `solid` without a Feynman pass. `ops.py calibration [TRACK]` reports confidence calibration; `ops.py prereqs "<concept>"` reports prerequisite state (`blocks` = a fuzzy direct prereq); `ops.py grade-mcq --key A,B,C --answers A,C,C` grades legacy probe MCQs deterministically (review/solo batches never use MCQs).
- `Learning System/Core/Learner History.md` — compact tutor background (fuzzy/neutral/solid per concept, generated by `scripts/learner_history.py`). Read this for learner context — never grep `Archive/`.
- `Learning System/Core/🧯 Mistakes.md` — structured wrong-answer ledger (error_type + self-attribution). Due mistakes are priority-1 in the review queue.
- `Learning System/Core/📦 Concept Archive.md` — paused/archived concepts. **Do not grep** — out of scope. Search only on explicit revive request.
- `Learning System/Sessions/`, `Learning System/Reviews/`, `Learning System/Lessons/`, `Learning System/Learning Records/` — writes land here.
- `Learning System/MISSION.md`, `Learning System/CURRICULUM.md`, `Learning System/GLOSSARY.md`, `Learning System/RESOURCES.md` — mission, curriculum, glossary, curated readings. The curriculum source is **a source, not the source**; enrich from its Further Reading.

## Teaching flow (delegation) — Scout → Tutor → Clerk

Trigger: "teach me X", "lesson", or "continue". The pipeline runs in the **same pi session**, delegating to subagents.

0. **Scout (new lesson only):** if no `Learning System/Lessons/Lesson — <slug> — *.md` exists for the requested topic/lesson and no `.tmp/context-<session_id>-<slug>.json` **within its 7-day TTL** is present, call the `scout` agent first: `dispatch({ agent: "scout", task: "<topic/lesson + why>" })`. Scout reads `MISSION.md`, `CURRICULUM.md`, `RESOURCES.md`, relevant Active Concepts rows, **and the curriculum source for the next lesson** — the live `phases/<phase>/<lesson>/docs/en.md` plus every URL in its `## Further Reading` (fetch loop: direct `curl -L --max-time 30` into `.tmp/`; PDFs → extract; YouTube → `yt-dlp --skip-download --write-auto-subs`; bot-blocked HTML → `curl https://r.jina.ai/<url>`; web search last). It hashes fetched bodies, compares to any prior digest hash, surfaces drift (`SCOUT DIGEST: ⚠️ Upstream changed`), and writes `Learning System/.tmp/context-<session_id>-<slug>.json` with `{goal, slug, tracks, concept_rows, prereqs, source_refs:[rohit_source, ...external_refs], rohit_hash, external_refs_hashes, failed_refs:[{url,reason}], lang_recommendation, fetched_at, roadmap_sha, synthesis}`. Every source/external ref carries `excerpt` (~500 chars) + `theory_excerpt` (the derivation/mechanism/assumptions passage, so the Tutor has the "why" in context) + `takeaways` + `adds_vs_rohit`; top-level `synthesis` is per-strand with a `theory` line (mechanism/derivation/assumptions/nearest-neighbour contrast for the foundation beat). Rohit = agenda, externals = enrichment. `prereqs` is load-bearing for the Tutor: `[{concept, keywords:[aliases/variants], why}]` covering every load-bearing dependency. Language per lesson `Languages:` header → `lang_recommendation` (Python / TypeScript / Rust). Scout posts a short `SCOUT DIGEST:` summary. The gate requires this digest for new lessons; resuming an existing `Lessons/` file bypasses it. **Lesson-start context audit (parent-owned, copies the ingest review-gate):** when Scout returns its `SCOUT_DIGEST` receipt, `dispatch` ONE independent `scout-audit` on the digest (`{"gate":"scout_audit","slug":"...","digest":"Learning System/.tmp/context-<session_id>-<slug>.json","raw_files":[...],"failed_refs":[...]}` — paths are enough, the auditor reads from disk) and fold its verdict before the first teaching turn. The gate withholds teaching claims until a valid audit exists (`NO_SCOUT_AUDIT_PASS`); an `ISSUES` verdict surfaces as a banner and never blocks — fix the digest via re-scout and re-audit until `PASS` (no cycle cap). **TTL (P2.3):** a digest older than 7 days is STALE and must be re-scouted before teaching new material from it — never treat a stale digest's source excerpts as authoritative (the state audit warns on TTL; the rule here is a hard requirement, not advisory).
1. Load `Learning System/MISSION.md` + `Learning System/CURRICULUM.md` to determine the next lesson (or the requested topic) — derive position per the position discipline above. If resuming (`Lessons/` file exists), the lesson file + last `Sessions/` note are the source of truth — no Scout digest needed.
2. **`lesson`/`continue`:** pick the next lesson per `CURRICULUM.md` (sequential within a mission). If resumable, resume where left off. A `done` lesson is never re-taught — retrieval-verify instead.
3. **`teach me X`:** in current-mission scope → treat as a curriculum node; out of scope → one-off that still feeds Pending Ingest for Clerk, and surface the "switching focus?" question.
4. Delegate the full interrogation flow (entry gate → closed-book spine check → triage → targeted attacks → model patch/clone) to the `learning-teach` skill. Claim/attack verification runs via **foreground** `fact-check` subagents; question batches via `quiz-audit`; grades via `grade-audit`; the graduation clone via `naive-student`. The Tutor **does not** write wiki pages, Active Concepts rows, or any position/state file (MISSION/CURRICULUM/Profile/Mistakes) — it writes its four handoff artifacts (lesson file, session note, learning record, `Pending Ingest.json`) in one batch at pause/lesson-end and hands off to the `clerk` subagent, which reconciles state at `/ingest`. Lesson end auto-ingests inline (`clerk` → `review-gate`); `/pause` is the exception and tells the learner to run `/ingest`.

## Review flow

Trigger: "review". The pipeline is **review-scout → Reviewer (main session) → review-clerk** in the same pi session. Run the review in the main session (it is interactive). Grades are verified via foreground `grade-audit` subagents — do not bypass.

Reviews test **cue selection and transfer**, not recognition: items are **unlabeled, interleaved, and trace-graded**. There are **no MCQs** in a review.

0. **Review Scout (always):** before the first review turn, dispatch `review-scout` (`dispatch({ agent: "review-scout", task: "<track, or 'active'>" })`). It runs the deterministic queue command (`python3 scripts/ops.py queue <track> --digest "Learning System/.tmp/review-${PI_SESSION_ID}-<track>.json"`) and fills in the current position. The digest's `queue` already carries every per-concept field (type, source, `last_q_type`, `question_type`, dates, mastery, Feynman status, due-mistake `error_type` + self-attribution) plus a grounded `source_excerpt`. The Reviewer does **not** gather state or build the queue itself. The gate withholds a review's first `claims`/`quiz` turn (`NO_REVIEW_CONTEXT`) until this run has happened; a partial digest surfaces a `⚠️ REVIEW CONTEXT INCOMPLETE` banner (never a withhold).
1. Track selection: `aiefs` / `aie` → the active track. If the user names an archived track, note it is archived and offer the active one. Neither → the active track.
2. Read the scout digest; if it is missing, fall back to ONE `python3 scripts/ops.py state <track> --review` call. Do not read the state files separately.
3. **The digest's `queue` IS the queue — use it verbatim.** Do not rebuild, re-sort, re-filter, or re-derive it; fewer than 5 entries is normal. **Before asking an entry, check its prerequisites (P1.3):** run `python3 scripts/ops.py prereqs "<concept>"`; if `blocks` is true, re-derive the fuzzy prerequisite first and defer the downstream item.
4. **Compose unlabeled trace items (no MCQs)** from the queue, presented as scenarios rather than one row per question:
   - **Never name the concept** when the item tests tool selection or application; naming is allowed only when the item directly tests a concept's meaning/anatomy.
   - **Multi-concept collisions:** with 3+ queue entries, compose 1–2 composite scenarios that chain concepts from different weeks (plus one known mistake), and grade each component concept separately. Record the scenario→concept mapping in the handoff, never shown to the learner.
   - **Decoy / near-miss:** at least one item whose surface vocabulary resembles a due concept but violates one of its `conditions`, so blind application fails.
   - **Cross-session collision** (when the digest carries `prior_knowledge`): compose at least one item that pits a due concept against the learner's own earlier verbatim model or an accepted graph proposition — ask which is right and what changed. Quote the prior words exactly as the digest carries them; never invent a past model, never announce the answer.
   - **Perturbation:** for at least one due concept, mutate a load-bearing assumption and ask for the qualitative downstream behaviour.
   - **Misapplication:** present a plausible real-world use where a `condition` is violated; the learner names the broken assumption and what should have been done instead.
   - For `concept`/`design` types, add a **teach-the-clone** item asking the learner to explain the (unlabeled) concept in their reply. Do **not** dispatch `naive-student` yet — there is nothing to teach it until the learner answers.
   - **Qualitative trace requirement:** instruct the learner to reply with the 3-line trace — cue & principle (why it applies) → mechanism/knob-turn → direction & extreme check — not only a final answer. No derivation or calculation prompts.
   - **Working trace:** the 3-line trace is the minimum, not a cap — a longer stream-of-consciousness working trace (thinking out loud, in chunks) is welcome. Grade the trace and infer whether the item was solved instead of demanding a final answer in a fixed form.
   - **Retrieval from an inactive state:** interleave the queue and never re-ask a concept immediately after its verdict — the item is still active, so retry later or in a fresh surface. Prefer items with the most **decision points** (junctures where a not-yet-active proposition must be chosen). Target retrieval that succeeds with effort (~85% per retrieval event) and rescue with the hint ladder rather than lowering the demand.
5. Present the whole batch in ONE `[[TURN:quiz]]` message so the learner can answer in one reply. Before showing it, dispatch ONE `quiz-audit` with `context:"review"`, `questions_json` (types `qualitative|synthesis|misapplication|perturbation|free_recall`), and `rendered_content` = the exact full batch text. Any issue (any severity) blocks: fix and re-audit until PASS — no cycle cap. **No visuals in the batch**: no widget, and no diagram that cues the method, until the answers are graded.
6. When the learner replies, build grade items with the learner's **trace** per item. If the batch contained a teach-the-clone item, dispatch **`naive-student`** now with the learner's teaching reply **verbatim** (`learner_transcript`), the concept, a seeded misconception, `prereq_level`, and a qualitative `target_task`; await `NAIVE_STUDENT_RECEIPT`. Then dispatch ONE batched `grade-audit` (`items[]`, one entry per answer) carrying `pow` (`perturbation|sabotage|clone|none`), `attack`, `qtype`, `confidence`, `trace`, `tutor_turns`, and `naive_student_receipt` on clone items. Use the verifier's per-item `correct_verdict`; on `agrees:false`, re-dispatch the corrected batch once and emit that. Do **not** present verdicts yet.
7. **Verified feedback + mandatory question pause.** Compose the learner-facing feedback (per item: verdict, the exact step that passed/slipped, the battery outcome, and one micro-check when a repair is needed) as prose plus the smallest visual that carries it (a table, a Mermaid causal chain, or a repair widget). Verify it with `fact-check` (`turn_kind:"grade_feedback"`, `grade_verdicts`, `visual_plan`, `rendered_content` = the exact feedback). Then present the feedback and **pause in the same turn** with an explicit invitation: *"Anything here that isn't clear — a verdict, the step you slipped on, or the repair? Ask now. If it's all clear, say 'no questions' and I'll save the session and ingest the results."* Stop the turn: do **not** dispatch `review-clerk`, do **not** ingest, and do **not** present the completion summary while the pause is open. Silence or a bare acknowledgement is not an explicit "no questions".
8. **Inquiry loop until the learner has no questions.** For every question, answer it as a normal tutoring turn (`fact-check` `turn_kind:"answer"` or `"repair"`, same visual discipline). If a question challenges a verdict, re-run `grade-audit` on that item and adopt the verifier's `correct_verdict`. Honor the hint discipline and "just tell me" (autopsy patch + one immediate perturbation, logged as `just_tell_me`). **Use the R0–R5 ladder** (`APPEND_SYSTEM.md`) for every hint: one rung per request, address the first break in their trace, statement repairs free, solution information metered; the rung needed is a difficulty readout. **When a fail is diagnosed, classify the miss** as `cue | discrimination | execution | careless | structural` and carry `miss_class` into the `REVIEW_WRITES.mistakes[]` row (the grade-audit already returns it; do not invent one). After answering, pause again with the same invitation. Advance only on an explicit "no questions" / "all clear" / "go ahead"; if ambiguous, ask once more.
9. **Persist (gate-enforced).** The Reviewer writes **no** state files. Dispatch ONE `review-clerk` with a `REVIEW_WRITES` envelope carrying the exact transcript, verifier verdicts, and feedback-pause inquiry:
   `dispatch({ agent: "review-clerk", task: { "gate":"review_writes", "track":"...", "date":"YYYY-MM-DD", "concepts":[...], "transcript":"exact Q/A + learner answers + traces + verifier verdicts + feedback/inquiry", "grade_verdicts":[{"concept":..,"correct_verdict":"pass|fail","miss_class":"cue|discrimination|execution|careless|structural|null","pow":"perturbation|sabotage|clone|none","q_type":"<enum>","confidence":"sure|hunch|no-idea","hints":N,"feynman":"feynman_pass|feynman_fail|none"}], "dependency_events":[...], "mistakes":[{"concept","error_type","miss_class":"cue|discrimination|execution|careless|structural","self_attribution","evidence"}], "digest":"Learning System/.tmp/review-<session_id>-<track>.json" } })`.
   Review-clerk records attempts (including battery outcomes), writes the Review note(s) + session note, updates the touched Active Concepts / Mistakes rows, runs `audit_state.py`, commits and pushes state only, and returns `REVIEW_CLERK_WRITES`.
10. **Review-session write audit (gate-enforced).** After review-clerk returns, dispatch ONE `review-session-audit` on the exact writes (`written_files` from the receipt's `reviews` + `session` + `state`; paths are enough). `PASS` releases the closing summary; an `ISSUES` verdict keeps it withheld (`REVIEW_SESSION_AUDIT_ISSUES`) until the writes are fixed and a fresh audit returns zero issues — no cycle cap. Scope is fenced: state drift the review did not write is `context_notes`, never a blocking issue.
11. **Completion summary.** Verify it with `fact-check` (`turn_kind:"answer"`) when substantial, then present per-concept verdicts and mastery movement, ingested/enriched wiki pages, new concepts and next review dates, and the state-audit result. Note open mistakes and what clears them. Do not claim completion if the auditor has not returned `PASS`.

The state audit is run by **review-clerk** before it returns; fold its `STATE_AUDIT_VERDICT: {"errors":N,"warnings":M}` verbatim. Review-clerk commits state only (`Learning System/`, `Knowledge Wiki/`).

## Solo flow

Trigger: "solo" / "AI-free check" / "closed-book". This is an unassisted operational check of the active track. The same deterministic queue and close as the review flow, but **no teaching, hints, repair prose, or widgets**, and **no MCQs**.

1. `[[FLOW:solo]]`. Dispatch `review-scout` to build the due queue; use it verbatim and check prerequisites.
2. Compose one closed-book batch from the queue: **unlabeled** operational items with the 3-line qualitative trace, at least one **perturbation**, one **misapplication**, one **decoy/near-miss**, and one **teach-the-clone** item for a `concept`/`design` entry. No MCQs, no calculation/derivation prompts.
3. Verify it with `quiz-audit` (`context:"solo"`), then present it with: *"Closed-book check. Work independently without hints or references. Include your 3-line qualitative trace for each item. Reply with your final answers."*
4. When the learner replies, dispatch `naive-student` for the clone item, then ONE batched `grade-audit` (`items[]`, with traces, `pow`, and `naive_student_receipt`). Report the verified Pass/Fail verdicts directly — **no repairs, no teaching**; a `[[TURN:none]]` one-line reminder is the only allowed message while the check is open.
5. Hand the durable writes to ONE `review-clerk` with `"mode":"solo"` (every attempt recorded AI-free, feeding the independence gate), then ONE `review-session-audit` on the exact writes. Report the score and updated mastery. The gate withholds `[[TURN:claims]]` as `SOLO_NO_TEACHING` and `[[TURN:ui]]` as `SOLO_NO_AIDS` by construction.

Intervals (type-aware): memory [0d,1d,3d,7d,14d,30d,60d] · concept [3d,7d,14d,30d] · procedure [3d,7d,14d] · design [14d,28d]. Mastery (advisory): memory/procedure quantitative; concept/design require a Feynman/clone pass.

## Ingest flow — via the clerk subagent (handoffs from Tutor and standalone `/ingest`)

Trigger: "ingest" with content to add (NOT a review). Delegate to the `clerk` subagent. Clerk reads `Pending Ingest.json` when the ingest originates from a lesson; standalone ingests pass the supplied content.

1. If `Learning System/Core/Pending Ingest.json` exists (lesson handoff), read it — it contains `{partial, status, resume_from, lesson_file, session_file, concepts, mistakes, source_url|source_file, created_at}` (`partial:true` for a `/pause` handoff, `partial:false` + `status:"done"` for a final lesson end). Use `lesson_file` as the source of content; `status`/`resume_from`/`concepts`/`mistakes` drive the state reconciliation in step 7b.
2. Otherwise extract concepts from the supplied content.
3. Overlap check — ONE bundle call with an alternation regex over candidate keywords: `python3 scripts/ops.py bundle "Learning System/Core/📚 Active Concepts.md@kw1|kw2|kw3"` (or `#^## <track>` for the full track section).
4. Overlap → enrich the existing wiki page + insight row with genuinely new details; set `last_reviewed` today; write the session note as enrichment (not new ingest). Read only the target page's relevant section (headings first via `@^## `).
5. No overlap → new concept: status `developing`, `last_reviewed` today, `next_review` +3d, `Last Q Type` `definitional`.
6. Outside focus area → ask about switching focus. Stagger schedules for multiple new concepts.
7. Persist EVERYTHING in one apply call (`ops.py apply` heredoc): wiki page(s), `index.md` update, `log.md` entry, session note. Clerk then extracts and merges the knowledge graph (`graph-extract` → `graph.py merge` → `graph.py status`) and reports it in `CLERK_WRITES.graph`; the parent runs the independent `graph-audit` on those records.
7b. **Reconcile position state from the handoff** (lesson handoffs): use `Pending Ingest.json`'s `status`/`resume_from`/`concepts`/`mistakes` as the single source to align the position pointers in `MISSION.md`, the `CURRICULUM.md` row, `💡 Learning Profile.md` (Current Focus / Current Position), and the `📚 Active Concepts.md` track header. Add handoff `concepts` missing from Active Concepts as new rows (developing, today, +3d, definitional); append handoff `mistakes[]` to `🧯 Mistakes.md` with canonical concept names; sync touched Active Concepts `next_review`/`last_reviewed` from `Attempts.json`; run `scripts/learner_history.py`. Surface (don't merge) any disagreement with the lesson file. Keep these out of the review-gate `target_files` — the state audit covers them.
8. **Independent review gate (parent-owned).** Clerk does NOT run the gate. When Clerk returns its `CLERK_WRITES: {"wiki":[...],"state":[...],"concepts":[...],"graph":{...},"commit":"..."}` receipt, the Tutor `dispatch`es ONE `review-gate` on the wiki pages Clerk wrote: `target_files:[{"path":"Knowledge Wiki/wiki/<page>.md"}, ...]` from `CLERK_WRITES.wiki` (omit `content`; the gate reads the files on disk), `out_of_scope` listing the state files, and `lesson_ref` when this came from a lesson. Fold its verdict. On any in-scope target issues (every severity blocks), re-dispatch Clerk with the fix (it writes + commits), then re-review until the verifier returns zero issues — **no cycle cap**, and NEVER re-dispatch review-gate for state/bookkeeping drift (findings in MISSION/CURRICULUM/Learning Profile/Learner History/Mistakes/Attempts/lesson/session/log/index are the state audit's job and are demoted to `context_notes`). Never hard-block on demoted review flags: out-of-scope findings are surfaced by the gate, not re-run.
8b. **Independent graph audit (parent-owned, when the Clerk wrote graph records).** If `CLERK_WRITES.graph` lists any created **or linked** nodes/chains, `dispatch` ONE `graph-audit` with a `GATE:graph_audit` envelope: `{"gate":"graph_audit","session":"<session id>","written_nodes":[created+linked node ids],"written_chains":[created+linked chain ids],"material":[...],"lesson_ref":"..."}` — the id lists from the Clerk's receipt, the material the extraction used, and the lesson file. Fold its verdict. On `ISSUES` (any severity), re-dispatch Clerk to RECORD A FIX (retract the offending id with a reason and re-merge a corrected record — a re-merged retracted id revives with its provenance unioned) — never hand-edit the ledgers — then re-audit until zero issues; **no cycle cap**. Graph bookkeeping outside the written ids is `context_notes`, not a blocker.
9. **State audit** is run by Clerk before it returns (`python3 "$HOME/learning-pi/pi/audit_state.py" --root .`); it fixes the error **or warning** findings it touched using the `STATE_AUDIT_FIXES` hints, re-runs once, surfaces hint-less/unrelated findings, and reports `STATE_AUDIT_VERDICT: {"errors":N,"warnings":M}`. Fold that verbatim.
10. **Close:** if `Pending Ingest.json` has `partial:true` (a `/pause` handoff), ingest today's concepts and KEEP both the `.tmp/context-*.json` digest and the lesson `in-progress` (clear only the marker, commit + push) — the digest's 7-day TTL still applies. Only a final (non-partial) ingest deletes the consumed digest, clears the marker, and lets the curriculum row go `done`.
11. **Final summary:** your post-clerk ingest summary is a `[[TURN:none]]` turn — start it with the tag and fold in the Tutor's `REVIEW_GATE_VERDICT` and Clerk's `STATE_AUDIT_VERDICT` markers. An untagged summary after a clerk dispatch is treated as an implicit `[[TURN:none]]` (verified by the review receipt), but tag it anyway.

### Handwritten notes

If the source is an image (handwritten notes, photo of a page), transcribe it verbatim before extraction:

- Use a vision-capable model (attach the image to the main session) to read the image, or ask the user to provide the text.
- Transcribe verbatim preserving structure (headings, bullets, diagrams in brackets); light cleanup only (fix obvious spelling, expand unambiguous abbreviations like 'bc' → 'because'); no rephrasing, summarization, or interpretation.
- Retry once on failure; if still failing, tell the user — never silently skip the image.

## End-of-session writes

These writes are owned by the **Clerk** (ingest) or **review-clerk** (review close) — never by the Tutor/Reviewer main session. Apply them in the delegated agent:

1. Update Active Concepts — statuses, dates, new concepts, open questions. Preserve existing rows.
2. On `consolidated`: move to `Archive/Consolidated/[concept].md` (name, date, insight, wiki link, related), remove from Active.
3. Write `Sessions/Session — [Topic] — [Date].md` (date, topic, concepts, statuses, open questions) with a one-line interleaving summary.
4. Consistency check — ONE bundle call re-grepping only the touched rows: `ops.py bundle "Learning System/Core/📚 Active Concepts.md@<concept1>|<concept2>" "Knowledge Wiki/index.md@<title>" "Knowledge Wiki/log.md:-3"`; verify today's `last_reviewed`, correct `next_review`, `Last Q Type`, all ingested concepts present, wiki pages in `index.md`, log entry present. Fix discrepancies in a single apply call. If the user claims stale dates are wrong, cross-check session notes.
5. Refresh learner context — run `python3 scripts/learner_history.py` (regenerates `Core/Learner History.md`).
6. Confirm completion — what was saved, what's due next.

## pi adaptation notes

- **Source of truth:** the repository working copy (current working directory). State lives in `Learning System/` and `Knowledge Wiki/`.
- **Pipeline:** `scout` → Tutor (main session) → `clerk`, all in one pi session; the review flow mirrors it as `review-scout` → Reviewer (main session) → `review-clerk`. Scout/review-scout write the ephemeral digest; Tutor/Reviewer teach/review; Clerk/review-clerk persist. Never write wiki pages/Active Concepts from the Tutor, and never write review state from the Reviewer.
- **Gate:** the `learning-gate` extension blocks unverified teaching/quiz/grade turns and enforces the Scout digest for new lessons. Fixed verifier wording lives in the verifier agent files — send data only.
- **State commits:** commit and push **state only** (`Learning System/`, `Knowledge Wiki/`) per `Learning System/AGENTS.md`. The pi control layer lives in a separate repository; do not commit it here.
