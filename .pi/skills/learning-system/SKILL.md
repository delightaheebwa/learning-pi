# Learning System

The active learning system, running in pi against the learning-system repository working copy (the current working directory).

**Trigger routing (read first):**
- **"review" → review flow** (active track). Runs in the main session.
- **"solo" / "AI-free check" / "closed-book" → solo flow** — a closed-book review of the active track where the gate withholds teaching (`SOLO_NO_TEACHING`) and figures (`SOLO_NO_AIDS`). Same deterministic queue and close as the review flow, but `review-clerk` records every attempt with `mode:"solo"` so it feeds the independence gate. Teaching and hints are impossible by construction; grade the closed-book answers only.
- **"teach me X" / "learn" / "study" → teaching loop** — use the `learning-teach` skill, NOT a review. "review" alone means the review flow.
- **"lesson" / "continue" → next curriculum lesson** — use the `learning-teach` skill.

**Position discipline (read first):** the current lesson/phase is **not** recorded in this skill. Derive it at runtime from `Learning System/CURRICULUM.md`, `Learning System/MISSION.md`, and the newest files in `Learning System/Lessons/` + `Learning System/Sessions/`. If those disagree, **STOP and report the contradiction to the user** before doing any work; do not guess or merge. (This repo has known stale statuses; treat the state files as the only source of position.)

**Turn tags (required — enforced by the gate):** begin every assistant message with `[[TURN:claims]]` (teaching/claims/plan), `[[TURN:quiz]]` (question batch), `[[TURN:grade]]` (grading a learner answer), `[[TURN:viz]]` (a ` ```viz ` spec + supporting words, verified by `viz-audit`), or `[[TURN:none]]` (transitions/summaries). The gate strips the tag before the learner sees it and withholds a message whose tag is missing or unsupported by a matching, passing verification receipt. A dropped tag is recovered from a bound receipt (`grade`/`quiz` from `grade-audit`/`quiz-audit`, `viz` from a `viz-audit` whose spec matches, `claims` from a `fact-check` whose `rendered_content` covers the text); `none` is never inferred. Dispatch each verifier **once per turn** with `dispatch({ agent, task: { ...envelope... } })` (foreground) — never re-verify the same draft; on a match/binding withhold, re-emit the verified text or fix the tag.

## Context discipline (hard rules — read first)

Sessions die when the running conversation outgrows the model's context window: every tool output stays in the transcript forever. The fix is fewer, denser tool calls — not smaller messages.

- **Batch all reads.** Never chain multiple full-file reads for state. Use the batch tool ONCE (`python3 scripts/ops.py ...`, paths are repo-root-relative):
  - Session start: `python3 scripts/ops.py state <track>` (reviews: `state <track> --review` for the compact profile + due queue)
  - Any mix of ranges/tails/greps: `python3 scripts/ops.py bundle "PATH:N-M" "PATH:-N" "PATH@regex1|regex2"`
- **Read wiki pages by section.** First `bundle "Knowledge Wiki/wiki/<page>.md@^## "` to list headings, then fetch only the section you enrich.
- **Batch all writes.** Persistence at session end = ONE apply call, not N writes:
  `python3 scripts/ops.py apply <<'SPEC'` then a JSON spec, then `SPEC`.
  Spec: `{"writes":[{"path","content"}],"appends":[{"path","content"}],"replaces":[{"path","find","replace_with"}]}`.
- Target **≤12 tool calls per flow**. Never re-read a file already in context. Never dump whole files you only need one row of. For git, use `git diff --stat` (not a full diff) and `git diff -- <path>` only for a file you need; do not switch models mid-flow (it invalidates the prompt cache and re-bills the whole context).

## State files (relative to the working repository root)

- `Learning System/Core/💡 Learning Profile.md` — learner preferences. Read at session start.
- `Learning System/Core/📚 Active Concepts.md` — per-track concept rows with `Type` (`memory | concept | procedure | design`). Type drives scheduler intervals. Grep/range only the needed track — never the whole file; `📦 Concept Archive.md` is out of scope.
- `Learning System/Core/Attempts.json` — evidence-based mastery sidecar (attempt history, interval_index state machine, Feynman pass). Bundled by `ops.py state`; report via `ops.py mastery <track>` — **advisory only** (scores shown, not blocking). `ops.py mastery` reports per-dimension scores (recall, conceptual, procedural, transfer, independence, stability) plus per-concept `calibration` and `transfer_ok`; a dimension with no evidencing attempt shows `—` (unknown), never 0. `ops.py attempt` accepts optional `--confidence sure|hunch|no-idea`, `--hints N`, `--mode normal|solo` (solo = AI-free), and `--prereq NAME` (repeatable); `--qtype` is an enum (unknown values rejected). A failed `mode=solo` attempt blocks the `solid` tag via the independence gate; a `concept`/`design` entry cannot be `solid` without a Feynman pass. `ops.py calibration [TRACK]` reports confidence calibration; `ops.py prereqs "<concept>"` reports prerequisite state (`blocks` = a fuzzy direct prereq); `ops.py grade-mcq --key A,B,C --answers A,C,C` grades MCQs deterministically.
- `Learning System/Core/Learner History.md` — compact tutor background (fuzzy/neutral/solid per concept, generated by `scripts/learner_history.py`). Read this for learner context — never grep `Archive/`.
- `Learning System/Core/🧯 Mistakes.md` — structured wrong-answer ledger (error_type + self-attribution). Due mistakes are priority-1 in the review queue.
- `Learning System/Core/📦 Concept Archive.md` — paused/archived concepts. **Do not grep** — out of scope. Search only on explicit revive request.
- `Learning System/Sessions/`, `Learning System/Reviews/`, `Learning System/Lessons/`, `Learning System/Learning Records/` — writes land here.
- `Learning System/MISSION.md`, `Learning System/CURRICULUM.md`, `Learning System/GLOSSARY.md`, `Learning System/RESOURCES.md` — mission, curriculum, glossary, curated readings. The curriculum source is **a source, not the source**; enrich from its Further Reading.

## Teaching flow (delegation) — Scout → Tutor → Clerk

Trigger: "teach me X", "lesson", or "continue". The pipeline runs in the **same pi session**, delegating to subagents.

0. **Scout (new lesson only):** if no `Learning System/Lessons/Lesson — <slug> — *.md` exists for the requested topic/lesson and no `.tmp/context-<session_id>-<slug>.json` (7-day TTL) is present, call the `scout` agent first: `dispatch({ agent: "scout", task: "<topic/lesson + why>" })`. Scout reads `MISSION.md`, `CURRICULUM.md`, `RESOURCES.md`, relevant Active Concepts rows, **and the curriculum source for the next lesson** — the live `phases/<phase>/<lesson>/docs/en.md` plus every URL in its `## Further Reading` (fetch loop: direct `curl -L --max-time 30` into `.tmp/`; PDFs → extract; YouTube → `yt-dlp --skip-download --write-auto-subs`; bot-blocked HTML → `curl https://r.jina.ai/<url>`; web search last). It hashes fetched bodies, compares to any prior digest hash, surfaces drift (`SCOUT DIGEST: ⚠️ Upstream changed`), and writes `Learning System/.tmp/context-<session_id>-<slug>.json` with `{goal, slug, tracks, concept_rows, prereqs, source_refs:[rohit_source, ...external_refs], rohit_hash, external_refs_hashes, failed_refs:[{url,reason}], lang_recommendation, fetched_at, roadmap_sha, synthesis}`. Every source/external ref carries `excerpt` (~500 chars) + `takeaways` + `adds_vs_rohit`; top-level `synthesis` is per-strand. Rohit = agenda, externals = enrichment. `prereqs` is load-bearing for the Tutor: `[{concept, keywords:[aliases/variants], why}]` covering every load-bearing dependency. Language per lesson `Languages:` header → `lang_recommendation` (Python / TypeScript / Rust). Scout posts a short `SCOUT DIGEST:` summary. The gate requires this digest for new lessons; resuming an existing `Lessons/` file bypasses it.
1. Load `Learning System/MISSION.md` + `Learning System/CURRICULUM.md` to determine the next lesson (or the requested topic) — derive position per the position discipline above. If resuming (`Lessons/` file exists), the lesson file + last `Sessions/` note are the source of truth — no Scout digest needed.
2. **`lesson`/`continue`:** pick the next lesson per `CURRICULUM.md` (sequential within a mission). If resumable, resume where left off. A `done` lesson is never re-taught — retrieval-verify instead.
3. **`teach me X`:** in current-mission scope → treat as a curriculum node; out of scope → one-off that still feeds Pending Ingest for Clerk, and surface the "switching focus?" question.
4. Delegate the full probe → plan → teach loop to the `learning-teach` skill. Claim verification runs via **foreground** `fact-check` subagents; question batches are audited via `quiz-audit` subagents before showing. The Tutor **does not** write wiki pages, Active Concepts rows, or any position/state file (MISSION/CURRICULUM/Profile/Mistakes) — it writes its four handoff artifacts (lesson file, session note, learning record, `Pending Ingest.json`) in one batch at pause/lesson-end and hands off to the `clerk` subagent, which reconciles state at `/ingest`.

## Review flow

Trigger: "review". The pipeline is **review-scout → Reviewer (main session) → review-clerk** in the same pi session. **Run the review in the main session** (it is interactive). Grades are verified via foreground `grade-audit` subagents — do not bypass.

0. **Review Scout (always):** before the first review turn, call the `review-scout` agent: `dispatch({ agent: "review-scout", task: "<track, or 'active'>" })`. It runs the deterministic queue command (`python3 scripts/ops.py queue <track> --digest "Learning System/.tmp/review-${PI_SESSION_ID}-<track>.json"`), then fills in the current position. The digest's `queue` already carries every per-concept field the Reviewer needs (type, source, `last_q_type`, `question_type`, dates, mastery, Feynman status, due-mistake `error_type` + self-attribution) plus a grounded `source_excerpt`. The Reviewer does **not** gather state or build the queue itself. The gate withholds a review's first `claims`/`quiz` turn (`NO_REVIEW_CONTEXT`) until this run has happened; a partial digest surfaces a `⚠️ REVIEW CONTEXT INCOMPLETE` banner (never a withhold).
1. Track selection: `aiefs` / `aie` → the active track. If the user names an archived track, note it is archived and offer the active one. Neither → the active track. (Review-scout reports the track; derive it the same way.)
2. Read the scout digest; if it is missing, fall back to ONE `python3 scripts/ops.py state <track> --review` call (compact profile + computed queue). Do not read the state files separately.
3. **The digest's `queue` IS the queue — use it verbatim.** Do **not** rebuild, re-sort, re-filter, or re-derive it; fewer than 5 entries is normal (only what is due is queued). Each entry's `question_type` is the deterministic alternation of its `last_q_type`. **Before asking an entry, check its prerequisites (P1.3):** run `python3 scripts/ops.py prereqs "<concept>"`; if `blocks` is true (a direct prereq is `fuzzy` or has an open mistake), do **not** grade the downstream concept as if it were independent — re-derive the fuzzy prereq first (ask it as the review item) and defer the downstream item.
4. Ask the whole queue in **ONE `[[TURN:quiz]]` message** — one question per entry, numbered — so the learner answers them all in one reply (the harness allows one subagent call per turn, so a single batch keeps the flow to one `quiz-audit` and one `grade-audit`). Target the 20% insight worth 80%, writing each question from that entry's `question_type` and `source_excerpt`. **Transfer cadence (P1.5):** for a `concept`/`design` entry whose last Q type was not a transfer type, include one `transfer-near`/`transfer-far` item (a novel context, not an isomorphic variant) on a cadence of at least every third review, so far-transfer evidence accumulates; record it with `--qtype transfer-far`. Math (paper accommodation): ask for the final result computed on paper — "Work on paper, reply with just the final number / chosen letter (A–D)." Never require typing full LaTeX/formulas verbatim. Correct final answer validates formula recall — do not skip math concepts.
5. Honor each entry's `question_type` from the digest; do not re-derive the alternation yourself.
5b. A `[[TURN:quiz]]` message requires a passing `quiz-audit` on **exactly the question(s) in that message**, dispatched before showing it — `dispatch({ agent: "quiz-audit", task: { "gate": "quiz_audit", "questions_json": [{"id":1,"type":"mcq|free_recall","question":..,"options":[...],"correct_index":N,"target_bloom":..}, ...], "rendered_content": "the exact full batch text", "purpose":"probe","concept":..} })`. Put every question you show in that message in `questions_json` **and** the full learner-facing batch in `rendered_content` (never `items[]`); the receipt binds the emission by 100% span coverage, so auditing a superset you do not show will not bind. Accept `PASS_WITH_FLAGS` silently (max 2 cycles).
6. After the learner's reply (which answers the whole batch): grade each item pass/fail, then verify with ONE `dispatch` of `grade-audit` before presenting anything. **Where the answer key is known (MCQ), grade mechanically first** — run `python3 scripts/ops.py grade-mcq --key A,B,C --answers A,C,C` and use its per-item result as the claimed verdict; the LLM only grades the free-recall items. Send ONE `grade-audit` envelope carrying every answer as an `items[]` entry (MCQ items with their code-derived `claimed_verdict`, free-recall items for semantic grading), then present the verifier's per-item `correct_verdict`; on `agrees:false`, re-dispatch the corrected batch once with `claimed_verdict` set to the verifier's `correct_verdict` and emit that.
   `dispatch({ agent: "grade-audit", task: { "gate":"grade_audit", "items":[{"id":1,"concept":..,"question":..,"learner_answer":..,"claimed_verdict":"pass|fail","source_excerpt":..,"feynman_transcript":..}, ...] } })` — `task` is the **envelope object**, never a JSON-encoded string; `dispatch` serializes it.
   A single answer may use the flat object shape `{ "gate":"grade_audit", "concept":..,"question":..,"learner_answer":..,"claimed_verdict":..,"source_excerpt":.. }`.
   **Grade turns take `grade_audit` ONLY — never `fact-check` for a grade.** If the verifier disagrees (`correct_verdict` differs), use its verdict. Do **not** run `ops.py attempt` or write any state yourself — the Reviewer records nothing; `review-clerk` records every verified verdict into `Attempts.json` at the close (step 9). For **every** `concept`/`design` entry, a Feynman explain-back (own words, when/why, nearest-neighbour distinction, one example) is a **required beat** — elicit it as a free-recall item and carry its `feynman_pass`/`feynman_fail` in the close envelope's `grade_verdicts[].feynman` so `review-clerk` records it. `learner_history.tag` cannot return `solid` for a `concept`/`design` without a Feynman pass (P1.1); `memory`/`procedure` are exempt.
7. Cap 5. Then ask "Any you want to dig deeper on?" — if yes, deep-dive one concept.
8. Surface open questions from Active Concepts. Also surface the advisory mastery line for each concept (e.g. `mastery 0.50 — Feynman: —`) alongside Held/Advanced for calibration.
9. **Hand off the writes to `review-clerk` (gate-enforced).** The Reviewer writes **no** state files. At the close, `dispatch` ONE `review-clerk` with a `REVIEW_WRITES` envelope carrying the exact transcript and verifier verdicts:
   `dispatch({ agent: "review-clerk", task: { "gate":"review_writes", "track":"...", "date":"YYYY-MM-DD", "concepts":[...], "transcript":"exact Q/A + learner answers + verifier verdicts", "grade_verdicts":[{"concept":..,"correct_verdict":"pass|fail","q_type":"<enum>","confidence":"sure|hunch|no-idea","hints":N,"feynman":"feynman_pass|feynman_fail|none"}], "mistakes":[{"concept","error_type","self_attribution","evidence"}], "digest":"Learning System/.tmp/review-<session_id>-<track>.json" } })`.
   Carry `q_type` (the enum value actually asked), `confidence` (the learner's tag), and `hints` (guiding questions given) on every `grade_verdicts` entry, and `feynman` for every `concept`/`design` entry — review-clerk passes them straight to `ops.py attempt` so the dimensions and calibration stay real.
   Review-clerk records attempts, writes the Review note(s) + session note, updates the touched Active Concepts / Mistakes rows, runs `audit_state.py` (fixing touched error/warning findings, re-running once), commits and pushes state only, and returns `REVIEW_CLERK_WRITES`. A completed review-clerk run arms the review-session audit gate below.
9b. **Review-session write audit (gate-enforced).** After review-clerk returns, `dispatch` ONE `review-session-audit` on the exact writes:
   `dispatch({ agent: "review-session-audit", task: { "gate":"review_session", "concepts":[...], "transcript":"exact Q/A + learner answers + verifier verdicts", "grade_verdicts":[{"concept":..,"correct_verdict":"pass|fail"}, ...], "written_files":[{"path":"Learning System/Reviews/..."},{"path":"Learning System/Sessions/..."},{"path":"Learning System/Core/📚 Active Concepts.md"},{"path":"Learning System/Core/🧯 Mistakes.md"},{"path":"Learning System/Core/Attempts.json"}], "state_rows":"..." } })` (`task` is the envelope **object**, never a JSON-encoded string). Build `written_files` from the `REVIEW_CLERK_WRITES` receipt's `reviews` + `session` + `state` entries; **paths are enough** — the auditor reads them from disk.
   The `learning-gate` arms this gate when review-clerk returns and withholds the closing summary until a receipt exists. `PASS`/`PASS_WITH_FLAGS` renders clean; `ISSUES` renders with a `⚠️ REVIEW FLAGS SURFACED` banner — never a withhold, never a re-run (hard cap **2 passes per flow**). Scope is fenced: findings in MISSION/CURRICULUM/Learning Profile/Learner History/`Knowledge Wiki/`/git are `context_notes`, never blocking issues.

The state audit is run by **review-clerk** before it returns; fold its `STATE_AUDIT_VERDICT: {"errors":N,"warnings":M}` verbatim (no separate `/audit` in the flow). Review-clerk commits state only (`Learning System/`, `Knowledge Wiki/`).

Intervals (type-aware): memory [0d,1d,3d,7d,14d,30d,60d] · concept [3d,7d,14d,30d] · procedure [3d,7d,14d] · design [14d,28d]. Mastery (advisory): memory/procedure quantitative; concept/design require Feynman pass.

## Ingest flow — via the clerk subagent (handoffs from Tutor and standalone `/ingest`)

Trigger: "ingest" with content to add (NOT a review). Delegate to the `clerk` subagent. Clerk reads `Pending Ingest.json` when the ingest originates from a lesson; standalone ingests pass the supplied content.

1. If `Learning System/Core/Pending Ingest.json` exists (lesson handoff), read it — it contains `{partial, status, resume_from, lesson_file, session_file, concepts, mistakes, source_url|source_file, created_at}` (`partial:true` for a `/pause` handoff, `partial:false` + `status:"done"` for a final lesson end). Use `lesson_file` as the source of content; `status`/`resume_from`/`concepts`/`mistakes` drive the state reconciliation in step 7b.
2. Otherwise extract concepts from the supplied content.
3. Overlap check — ONE bundle call with an alternation regex over candidate keywords: `python3 scripts/ops.py bundle "Learning System/Core/📚 Active Concepts.md@kw1|kw2|kw3"` (or `#^## <track>` for the full track section).
4. Overlap → enrich the existing wiki page + insight row with genuinely new details; set `last_reviewed` today; write the session note as enrichment (not new ingest). Read only the target page's relevant section (headings first via `@^## `).
5. No overlap → new concept: status `developing`, `last_reviewed` today, `next_review` +3d, `Last Q Type` `definitional`.
6. Outside focus area → ask about switching focus. Stagger schedules for multiple new concepts.
7. Persist EVERYTHING in one apply call (`ops.py apply` heredoc): wiki page(s), `index.md` update, `log.md` entry, session note.
7b. **Reconcile position state from the handoff** (lesson handoffs): use `Pending Ingest.json`'s `status`/`resume_from`/`concepts`/`mistakes` as the single source to align the position pointers in `MISSION.md`, the `CURRICULUM.md` row, `💡 Learning Profile.md` (Current Focus / Current Position), and the `📚 Active Concepts.md` track header. Add handoff `concepts` missing from Active Concepts as new rows (developing, today, +3d, definitional); append handoff `mistakes[]` to `🧯 Mistakes.md` with canonical concept names; sync touched Active Concepts `next_review`/`last_reviewed` from `Attempts.json`; run `scripts/learner_history.py`. Surface (don't merge) any disagreement with the lesson file. Keep these out of the review-gate `target_files` — the state audit covers them.
8. **Independent review gate (parent-owned).** Clerk does NOT run the gate. When Clerk returns its `CLERK_WRITES: {"wiki":[...],"state":[...],"concepts":[...],"commit":"..."}` receipt, the Tutor `dispatch`es ONE `review-gate` on the wiki pages Clerk wrote: `target_files:[{"path":"Knowledge Wiki/wiki/<page>.md"}, ...]` from `CLERK_WRITES.wiki` (omit `content`; the gate reads the files on disk), `out_of_scope` listing the state files, and `lesson_ref` when this came from a lesson. Fold its verdict. On high/medium target issues, re-dispatch Clerk with the fix (it writes + commits), then re-review once — **max 2 review cycles, never a third, and NEVER re-dispatch review-gate for state/bookkeeping drift** (findings in MISSION/CURRICULUM/Learning Profile/Learner History/Mistakes/Attempts/lesson/session/log/index are the state audit's job and are demoted to `context_notes`). Never hard-block on review flags: an `ISSUES`/`PASS_WITH_FLAGS` verdict is surfaced by the gate, not re-run.
9. **State audit** is run by Clerk before it returns (`python3 "$HOME/learning-pi/pi/audit_state.py" --root .`); it fixes the error **or warning** findings it touched using the `STATE_AUDIT_FIXES` hints, re-runs once, surfaces hint-less/unrelated findings, and reports `STATE_AUDIT_VERDICT: {"errors":N,"warnings":M}`. Fold that verbatim.
10. **Close:** if `Pending Ingest.json` has `partial:true` (a `/pause` handoff), ingest today's concepts and KEEP both the `.tmp/context-*.json` digest and the lesson `in-progress` (clear only the marker, commit + push) — the digest's 7-day TTL still applies. Only a final (non-partial) ingest deletes the consumed digest, clears the marker, and lets the curriculum row go `done`.
11. **Final summary:** your post-clerk ingest summary is a `[[TURN:none]]` turn — start it with the tag and fold in the Tutor's `REVIEW_GATE_VERDICT` and Clerk's `STATE_AUDIT_VERDICT` markers. An untagged summary after a clerk dispatch is treated as an implicit `[[TURN:none]]` (verified by the review receipt), but tag it anyway.

### Handwritten notes

If the source is an image (handwritten notes, photo of a page), transcribe it verbatim before extraction:

- Use a vision-capable model (attach the image to the main session) to read the image, or ask the user to provide the text.
- Transcribe verbatim preserving structure (headings, bullets, diagrams in brackets); light cleanup only (fix obvious spelling, expand unambiguous abbreviations like 'bc' → 'because'); no rephrasing, summarization, or interpretation.
- Retry once on failure; if still failing, tell the user — never silently skip the image.

## End-of-session writes

These writes are owned by the **Clerk** (ingest) or **review-clerk** (review close) — never by the Tutor/Reviewer main session. Apply them in the delegated agent:

1. Update Active Concepts — statuses, dates, new concepts, open questions. Preserve existing rows.
2. On `consolidated`: move to `Archive/Consolidated/[concept].md` (name, date, insight, wiki link, related), remove from Active.
3. Write `Sessions/Session — [Topic] — [Date].md` (date, topic, concepts, statuses, open questions) with a one-line interleaving summary.
4. Consistency check — ONE bundle call re-grepping only the touched rows: `ops.py bundle "Learning System/Core/📚 Active Concepts.md@<concept1>|<concept2>" "Knowledge Wiki/index.md@<title>" "Knowledge Wiki/log.md:-3"`; verify today's `last_reviewed`, correct `next_review`, `Last Q Type`, all ingested concepts present, wiki pages in `index.md`, log entry present. Fix discrepancies in a single apply call. If the user claims stale dates are wrong, cross-check session notes.
5. Refresh learner context — run `python3 scripts/learner_history.py` (regenerates `Core/Learner History.md`).
6. Confirm completion — what was saved, what's due next.

## pi adaptation notes

- **Source of truth:** the repository working copy (current working directory). State lives in `Learning System/` and `Knowledge Wiki/`.
- **Pipeline:** `scout` → Tutor (main session) → `clerk`, all in one pi session; the review flow mirrors it as `review-scout` → Reviewer (main session) → `review-clerk`. Scout/review-scout write the ephemeral digest; Tutor/Reviewer teach/review; Clerk/review-clerk persist. Never write wiki pages/Active Concepts from the Tutor, and never write review state from the Reviewer.
- **Gate:** the `learning-gate` extension blocks unverified teaching/quiz/grade turns and enforces the Scout digest for new lessons. Fixed verifier wording lives in the verifier agent files — send data only.
- **State commits:** commit and push **state only** (`Learning System/`, `Knowledge Wiki/`) per `Learning System/AGENTS.md`. The pi control layer lives in a separate repository; do not commit it here.
