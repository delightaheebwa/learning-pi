## Findings

### [MEDIUM] `ops.py attempt --prereq` replaces the edge list instead of merging it
- Where: `learning-system/scripts/ops.py` (`do_attempt`: `entry["prereqs"] = [p for p in prereqs if p]`)
- Evidence: code excerpt above; `do_prereqs --set` replace-semantics are documented
  ("--set writes the prereq list"), but `--prereq` on `attempt` is documented as "records the
  concept's direct prerequisite edges" with no merge warning. A Tutor recording one prereq
  per attempt silently drops earlier edges.
- Why it matters: the prerequisite graph silently loses edges under normal use; a blocking
  `fuzzy` prereq can disappear from the list and stop blocking. Fails open, so not high —
  but it corrupts the exact state P1.3 exists to build.
- Recommended fix: merge in `do_attempt` (`entry["prereqs"] = sorted(set(existing) | set(prereqs))`);
  keep replace-semantics only behind `prereqs --set`. Add an `ops_test` case.

### [MEDIUM] Far-transfer items are never scheduled by deterministic code
- Where: `learning-system/scripts/ops.py:574-577` (`_question_type` alternates only
  `definitional`↔`discriminative`); review skill (`.pi/skills/learning-system/SKILL.md`)
  asks for a `transfer-near`/`transfer-far` item "on a cadence of at least every third review".
- Evidence: `grep transfer` in `ops.py` shows the dimension/grading side only; the queue
  path (`_queue_entry`, `_question_type`) can never emit a transfer `question_type`. The
  "authoritative, use verbatim" queue therefore never contains the item the skill asks for —
  the Tutor must disobey the verbatim-queue instruction to satisfy the cadence instruction.
- Why it matters: P1.5's scheduling half is prompt-deep only; far-transfer evidence (which
  gates `consolidated`) accumulates only if the LLM improvises against its own queue rule.
- Recommended fix: either teach `_question_type`/queue about transfer cadence deterministically
  (e.g. every Nth review of a `concept`/`design` emits `transfer-far`), or downgrade the roadmap
  claim to "Tutor may include" and note the contradiction with the verbatim-queue rule.

### [MEDIUM] Feynman "mandatory beat" is prompt-mandatory, code-advisory
- Where: `.pi/skills/learning-system/SKILL.md` (step 6), `.pi/agents/review-clerk.md`,
  `.pi/prompts/review.md` vs `scripts/learner_history.py:tag()`.
- Evidence: `grep -rn feynman gate-core/` returns only a summary-line regex
  (`primitives.ts:698`); no gate or clerk code validates that a `concept`/`design` close
  envelope carries `feynman_pass`/`feynman_fail`. A review can close with `feynman:none`
  and nothing rejects it — the concept merely stays `neutral`.
- Why it matters: the brief's "Reviews must elicit it" is enforced only by LLM obedience,
  the exact failure mode (`feynman: none` in practice) the audit flagged. What *is* hard is
  the outcome gate — `tag()` cannot return `solid` for `concept`/`design` without
  `feynman_pass` (verified in code + `TestLearnerHistoryFeynmanGate`) — so graduation is
  protected but the elicitation beat itself is not.
- Recommended fix: add a code check where the envelope lands — e.g. `review-clerk`'s
  `ops.py attempt` call path or a `learner_history`/audit warning when a `concept` review
  closes with `feynman:none` — or scope the roadmap claim down to "graduation-gated".

### [MEDIUM] Hard-fact withhold fires on content, not on verification state (over-withholds verified turns)
- Where: `learning-pi/.pi/extensions/learning-gate/gate-core/engine.ts` (legacy retry-cap
  block; judge path `turnType === "claims" && extractHardFacts(text).length > 0`).
- Evidence: the condition inspects only whether the *text* contains hard facts, not why the
  turn was blocked. A claims turn carrying a valid passing fact-check but blocked on an
  unrelated reason (e.g. `NO_SCOUT_CONTEXT`, `NO_REVIEW_CONTEXT`) hits the cap and is
  **withheld entirely** instead of delivered `⛔ UNVERIFIED` — verified numbers/formulas are
  suppressed because of a bookkeeping block. P0.2's `CLAIMS_INCOMPLETE` already guarantees
  listed facts went before a verifier in exactly this scenario.
- Why it matters: availability regression for the safest case (verified content, unrelated
  block); the withhold is broader than its justification ("a number nobody verified").
- Recommended fix: withhold only when the block set implicates verification
  (`NO_FACT_CHECK_MATCH`, `FACT_CHECK_PENDING`, `CLAIMS_INCOMPLETE`, `FACT_CHECK_ISSUES`-family);
  keep `UNVERIFIED`-delivery for scout/context-only blocks. Add a gate test for the
  verified-but-no-scout case.

### [MEDIUM] Red-team harness measures gate plumbing, not verifier judgment — headline overstates it
- Where: `learning-pi/test/redteam/redteam_test.mjs`; `AUDIT-ROADMAP.md` P1.8
  ("asserts the gate catches it").
- Evidence: 4 of 5 seeded errors are caught via `CLAIMS_INCOMPLETE` — i.e. they re-exercise
  P0.2's deterministic completeness rule, which already had tests. The 5th (wrong attribution)
  is "caught" because the harness itself authors both the error *and* the `ISSUES` verdict;
  the synthetic verifier never has to detect anything. There is no case where all hard facts
  are listed but wrong and the verifier passes them (the F1/F4 path from the audit) — such a
  case would sail through, and the harness cannot see it.
- Why it matters: `caught 5/5` reads as a false-verification-rate measurement (audit §17's
  goal) but the harness is structurally incapable of failing on correlated generator/verifier
  error — the audit's top epistemic risk. The roadmap claim should not imply otherwise.
- Recommended fix: add a documented known-limitation case — listed-but-false claim with a
  `PASS` verifier receipt, asserted to *render* (proving the harness can observe F1/F4, not
  just plumbing) — and reword the roadmap line to "measures deterministic catch paths +
  receipt plumbing; does not measure verifier judgment".

### [MEDIUM] `--confidence` end-to-end recording relies on LLM obedience with no check
- Where: `.pi/agents/review-clerk.md`, `.pi/skills/learning-teach/SKILL.md`,
  `learning-system/scripts/ops.py` (`normalize_confidence`, `compute_calibration`).
- Evidence: nothing in code requires `confidence` on a graded attempt — `do_attempt`
  accepts its absence, and `compute_calibration` silently ignores untagged history. If the
  Reviewer/Tutor omits the tag, calibration degrades to "no confidence-tagged attempts" with
  no error surfacing which flow dropped it. The math itself is correct (verified: `sure`
  wrong-rate > 0.3 with n≥3 → `overconfident`; `hunch` ≥ 0.75 → `underconfident`;
  per-concept calibration present in `mastery --json`).
- Why it matters: P1.4's "flows record `--confidence` on every graded attempt" is, like the
  Feynman beat, prompt-deep; missing data is silent and per-flow attribution is absent.
- Recommended fix: warn when recording a graded attempt without `--confidence`
  (or count untagged attempts in `do_calibration` output), so drops are visible.

### [LOW] `grade-mcq` accepts arbitrary non-letter tokens without complaint
- Where: `learning-system/scripts/ops.py` (`do_grade_mcq` — no token validation).
- Evidence: `ops.py grade-mcq --key "A1,B?" --answers "A1,B?"` → `2/2 correct`. Case/whitespace
  handling is good (verified); letter-ness is unchecked, so a malformed key from a Reviewer
  (e.g. `correct_index` passed raw) grades garbage as PASS.
- Why it matters: minor; mechanical grading should reject mechanical nonsense.
- Recommended fix: validate tokens against `^[A-E]$` (or the MCQ option range) with exit 2.

### [LOW] `normalize_confidence` accepts any string as a bucket
- Where: `learning-system/scripts/ops.py` (`normalize_confidence` — "Unknown values are
  returned lowercased, never rejected (back-compat)").
- Evidence: `--confidence maybe` stores a `maybe` bucket that `do_calibration` then prints.
- Why it matters: typo'd levels (`suree`, `hunch?`) fragment calibration silently.
- Recommended fix: warn-and-store (or reject) unknown levels; document the accepted set in
  the `attempt` usage line.

### [LOW] P1.7 section-level `status=learner-note` is not machine-checkable
- Where: `.pi/skills/llm-wiki/SKILL.md` (P1.7 sample shape), `Knowledge Wiki/AGENTS.md`.
- Evidence: P0.6 tooling (`wiki_provenance.py --check`) validates a single page-level marker;
  the per-section `status=learner-note` marker lives inside prose and no check reads it.
- Why it matters: a missing/mis-marked learner section is unverifiable except by reading;
  matches the brief ("no code gate needed"), but the provenance claim exceeds the tooling.
- Recommended fix: extend `wiki_provenance.py --check` to flag `## My understanding` sections
  lacking the learner-note marker, or scope the claim to convention.

### [LOW] Roadmap P1.2 wording overstates the grade-audit change
- Where: `AUDIT-ROADMAP.md` P1.2 ("sends only free-recall to `grade-audit`").
- Evidence: the review skill still sends ONE batched `grade-audit` envelope with every answer
  as an `items[]` entry — MCQ items ride along with code-derived `claimed_verdict`s; the LLM
  verifier still sees (and can dispute) them.
- Why it matters: small doc/implementation drift; the design (mechanical first, LLM verifies)
  is sound, but "only free-recall" is false and a future agent may build on it.
- Recommended fix: reword to "MCQ verdicts precomputed with `grade-mcq`; `grade-audit`
  verifies the batch".

No high findings. No P0 regressions found (contract coverage intact, `G-retry-cap`
semantics preserved for grade/quiz/none turns per the golden test, legacy stored attempts
keep counting via retained alias spellings in the dimension sets).

## Verdict

P1 does most of what the roadmap claims and is honest about its two deferrals
(`consolidated` graduation flow; deterministic hint-fade check). The deterministic core is
solid: the q_type enum rejects unknown values without breaking stored attempts, the MCQ
grader is correct on mixed/empty/mismatched inputs, prereq unknown-never-blocks holds, the
calibration math is right, retry-cap withhold keeps content out while sparing prose, and the
red-team harness runs green inside `learn-check`. But three of the nine items are
prompt-deep rather than enforced — the Feynman beat, far-transfer scheduling (which
contradicts the verbatim-queue rule), and confidence recording — and the red-team 5/5
headline measures P0.2's completeness check more than any new detection power. The single
most important fix is the `--prereq` replace-vs-merge bug: it is the only finding that
silently corrupts state, in the exact subsystem P1.3 was built to create.
