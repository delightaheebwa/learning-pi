Make failure useful.

A test is a small executable question about your program. Today you will write one, see it fail, fix the code, and make the process repeatable.

Arrange, Act, Assert

A focused test has three recognizable movements:

PhaseQuestion
ArrangeWhat inputs and starting state do I need?
ActWhich function or command am I checking?
AssertWhat observable result should be true?

Keeping the phases visible prevents a test from becoming a second, tangled implementation of the feature.

Build a tiny runner

There is no framework yet. The operating system already gives us two useful test-runner behaviors: an assertion stops the process when it is false, and the process exit code tells the shell whether it succeeded.

#include <assert.h>

static int add(int left, int right)
{
    return left + right;
}

static void test_adds_two_numbers(void)
{
    /* Arrange */
    int left = 2;
    int right = 3;

    /* Act + Assert */
    assert(add(left, right) == 5);
}

int main(void)
{
    test_adds_two_numbers();
    return 0;
}

Compile and run it:

gcc -Wall -Wextra -std=c17 -g test_add.c -o test_add
./test_add
echo $?

Now change the expected value from 5 to 6. The assertion should print a failure and the shell should show a nonzero exit status. That is red: the test has exposed a mismatch.

Red, green, refactor. Red means a test fails for a meaningful reason. Green means the behavior is protected. Refactor means improve the design without changing the protected behavior. The loop is useful even when you do not practice formal TDD every minute.

Practice: test a boundary

  1. Add test_adds_a_negative_number.
  2. Add test_zero_is_an_identity.
  3. Break add deliberately, run the test, and read the failure.
  4. Repair add and confirm the program exits with status zero.

Say the three phases aloud for one of your tests. If you cannot point to the Act, the test may be checking too much at once.

Why this matters for procfs

Our monitor will read changing operating-system files. We will not try to assert that the live machine has one exact amount of RAM. Instead, we will separate reading from parsing, then give the parser stable text in a fixture. That is the testable seam.

Primary reading: Our First Tests (and Bugs). It shows a real C project discover a bug through a failing test. For the vocabulary, read Bill Wake's Arrange, Act, Assert.
