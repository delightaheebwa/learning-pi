# Maintenance Mindset

The recognition that **we are always in maintenance mode**. Software is never "finished" — our thinking and understanding about it changes day by day.

## Core idea

There is no clean split between "development" and "maintenance." From the moment you write the first line, you're maintaining it. Requirements change, your understanding deepens, edge cases emerge, dependencies update. Every change is maintenance.

## Implications

- **Design for change from day one**: See [[ETC (Easier To Change)]]
- **Your code will outlive your current understanding**: Write it so future-you (or a teammate) can understand it
- **"Done" is temporary**: The software that works perfectly today will need changes tomorrow
- **Refactoring is maintenance, not a separate activity**: It's continuous, not a special project

## The mental shift

Instead of thinking "I'm building this and then it's done," think "I'm maintaining this from the moment I start." This changes how you name things, how you structure code, and how you document decisions.
