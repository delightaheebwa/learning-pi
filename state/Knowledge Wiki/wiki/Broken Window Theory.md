# Broken Window Theory

A software development principle adapted from criminology: one "broken window" (messy code, ignored bug, hacky workaround) signals that nobody cares, which invites more neglect and accelerates decay.

## Core idea

Don't leave messes unfixed. If you discover something broken or messy — fix it immediately. If there isn't time for a full fix, do something visible to show you're on top of it (board it, add a comment/ticket, flag it).

## Why it matters

People are more likely to keep something neat if it's already neat. A clean codebase stays clean because nobody wants to be the first to mess it up. A messy codebase gets messier because "what's one more hack?"

## Key rules

- Fix issues as soon as they come up
- If you can't fix it now, at least acknowledge it (comment, ticket, note)
- Avoid collateral damage — don't let one broken window spread
- Don't be the one who breaks the first window
